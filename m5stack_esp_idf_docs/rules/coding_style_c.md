# 組み込みC言語 コーディング規約

このドキュメントは、ESP-IDFを用いた組み込みC言語開発におけるコーディング規約とベストプラクティスを定義します。目標は、信頼性、保守性、効率性の高いコードを生成することです。

## 1. データ型

*   **固定幅整数型の使用**: `int`や`long`のようなプラットフォーム依存の型ではなく、常に`stdint.h`で定義される固定幅整数型（例: `uint8_t`, `int32_t`, `size_t`）を使用してください。これにより、コードの意図が明確になり、移植性が向上します。
    ```c
    // 良い
    uint32_t loop_count = 1000;
    int16_t temperature;

    // 悪い
    long loop_count = 1000;
    int temperature;
    ```
*   **符号の意識**: データが負の値を取らないことが確実な場合は、`unsigned`型（`uintX_t`）を使用してください。

## 2. 変数と定数

*   **初期化**: 変数は必ず宣言時に意味のある値で初期化してください。
    ```c
    // 良い
    uint8_t buffer[128] = {0};
    int ret = ESP_OK;

    // 悪い
    uint8_t buffer[128]; // 不定な値が含まれる
    ```
*   **スコープの最小化**: 変数は可能な限り狭いスコープ（例: forループ内、関数内）で宣言してください。グローバル変数の使用は最小限に留めてください。
*   **`static`の活用**: ファイルスコープの変数や関数には`static`を付け、外部からのアクセスを制限してください。
*   **`const`の徹底**: 変更されない変数には常に`const`を付けてください。これにより、コンパイラが最適化を行い、誤った変更を防ぐことができます。これはRAMの使用量を削減し、データをFlashに配置するのにも役立ちます。

## 3. 関数

*   **単一責任の原則**: 関数は一つの明確なタスクのみを行うように設計してください。20〜30行を超える関数は、分割を検討してください。
*   **明確な命名**: 関数の動作がわかるような、動詞を含む名前を付けてください。（例: `spi_read_sensor`, `display_draw_rectangle`）
*   **引数の検証**: ポインタを引数として受け取る関数では、必ず`NULL`チェックを行ってください。
    ```c
    esp_err_t process_data(const data_t *data) {
        if (data == NULL) {
            return ESP_ERR_INVALID_ARG;
        }
        // ... 処理 ...
        return ESP_OK;
    }
    ```

## 4. プリプロセッサとマクロ

*   **`static inline`の優先**: 複数の文を含むような複雑なマクロよりも、`static inline`関数を優先してください。これにより、型チェックが働き、デバッグが容易になります。
*   **マクロ引数の括弧**: マクロを定義する際は、すべての引数を括弧で囲み、予期せぬ評価順序を防いでください。
    ```c
    // 良い
    #define SQUARE(x) ((x) * (x))

    // 悪い
    #define SQUARE(x) x * x
    ```
*   **マジックナンバーの回避**: コード中に直接数値を記述せず、`#define`や`const`変数を使用して名前を付けてください。

## 5. エラーハンドリング

*   **`esp_err_t`戻り値**: 失敗する可能性のある関数（特にドライバやAPI呼び出し）は、`esp_err_t`を返すように設計してください。`ESP_OK`を成功、その他の`ESP_ERR_...`をエラーとして返します。
*   **戻り値のチェック**: 外部関数やドライバ関数を呼び出した後は、必ずその戻り値を確認してください。
*   **`ESP_ERROR_CHECK()`の使用**: 回復不可能な致命的なエラーが発生した場合に`ESP_ERROR_CHECK()`マクロを使用してください。このマクロは、エラーが発生するとプログラムを停止させ、問題の箇所をログに出力します。回復可能なエラーには使用しないでください。
    ```c
    // 致命的なエラー（I2Cバスの初期化失敗など）
    ESP_ERROR_CHECK(bsp_i2c_init());

    // 回復可能なエラー
    esp_err_t ret = read_sensor_data();
    if (ret != ESP_OK) {
        ESP_LOGW(TAG, "Failed to read sensor, using default value. Error: %s", esp_err_to_name(ret));
        // ... フォールバック処理 ...
    }
    ```

## 6. 可読性とコメント

*   **コメントは「なぜ」を説明する**: コードが「何をしているか」はコード自体が示すべきです。コメントは、そのコードが存在する理由、設計上の決定、複雑なアルゴリズムの背景などを説明するために使用してください。
*   **一貫したスタイル**: プロジェクト全体で一貫したインデント（例: スペース4つ）とブレースのスタイル（例: K&Rスタイル）を維持してください。
*   **`//` vs `/* ... */`**: 単行コメントには`//`、複数行のコメントや関数のヘッダには`/* ... */`を使用してください。

## 7. MISRA Cへの言及

このプロジェクトではMISRA Cガイドラインの厳格な遵守は要求しませんが、その思想は高品質な組み込みソフトウェアの基本です。特に以下の原則は、安全性が求められるコンポーネントで考慮する価値があります。

*   動的メモリ割り当て（`malloc`, `free`）の制限。
*   再帰呼び出しの禁止。
*   ポインタ演算の制限。
*   暗黙的な型変換の回避。

これらのルールを意識することは、より予測可能で堅牢なコードにつながります。
