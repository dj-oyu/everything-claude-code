# FreeRTOS利用パターンとルール

このドキュメントは、ESP-IDF環境でFreeRTOSを使用する際の主要なパターン、ルール、およびベストプラクティスを定義します。これらの指針に従うことで、応答性が高く、安定的で、保守しやすいマルチタスクアプリケーションを構築できます。

## コア原則: ノンブロッキングで疎結合な設計

*   **応答性の維持**: CPUを独占するような「ビジーウェイト」を避け、ブロッキングAPI（`vTaskDelay`やタイムアウト付きのセマフォ/キュー待ち）を使用してCPUを他のタスクに明け渡してください。
*   **タスクの独立性**: 各タスクは単一の明確な責務を持つように設計し、タスク間の結合はキューやセマフォなどの明確なインターフェースを介して行います。グローバル変数によるタスク間通信は極力避けてください。

## 1. タスク (`xTaskCreate` / `xTaskCreatePinnedToCore`)

*   **単一責任**: 各タスクは、センサーの読み取り、UIの更新、ネットワーク通信など、一つの明確な役割に集中させるべきです。
*   **優先順位**:
    *   意味のある優先順位を付けてください (`tskIDLE_PRIORITY` + N)。
    *   リアルタイム性が要求されるタスク（例: モーター制御）には高い優先順位を、そうでないタスク（例: UIの更新）には低い優先順位を付けます。
    *   多くのタスクを同じ高い優先順位に設定することは避けてください。
*   **スタックサイズ**: `uxTaskGetStackHighWaterMark()`を使用して、実行後のスタックの最高水位を確認し、必要最低限のスタックサイズを設定します。過剰な割り当てはRAMの無駄遣いです。
*   **タスクのメインループ**: タスク関数は`while(1)`ループを本体とし、決してリターンしてはいけません。
*   **タスクの終了**: タスクが自己終了する必要がある場合は、`vTaskDelete(NULL)`を呼び出します。その前に、確保したメモリやリソースをすべて解放する必要があります。

## 2. 同期プリミティブ

### ミューテックス (`xSemaphoreCreateMutex`)

*   **用途**: 共有リソース（グローバル変数、ペリフェラルなど）を複数のタスクからの同時アクセスから保護するために使用します。
*   **ルール**:
    *   `xSemaphoreTake()`でミューテックスを取得したら、できるだけ短い時間で処理を終え、**必ず**`xSemaphoreGive()`で返却してください。
    *   ミューテックスで保護されたクリティカルセクション内でブロッキングAPI（`vTaskDelay`など）を呼び出すことは避けてください。
    *   優先順位の逆転問題に注意してください。

### バイナリセマフォ (`xSemaphoreCreateBinary`)

*   **用途**: タスク間の単純なシグナリング、または割り込みサービスルーチン（ISR）からタスクへの通知（例: 「データ受信完了」）に使用します。
*   **パターン**: タスクは`xSemaphoreTake()`を（通常はタイムアウト付きで）呼び出して待機し、ISRまたは他のタスクが`xSemaphoreGiveFromISR()` / `xSemaphoreGive()`を呼び出してタスクを起動します。

### カウンティングセマフォ (`xSemaphoreCreateCounting`)

*   **用途**: 利用可能な数が限られているリソース（例: コネクションプール、バッファプール）の管理に使用します。

## 3. タスク間データ通信

### キュー (`xQueueCreate`)

*   **用途**: タスク間でデータを安全に渡すための**推奨される**方法です。キューはスレッドセーフ（タスクセーフ）であり、FIFO（先入れ先出し）の順序を保証します。
*   **ルール**:
    *   ポインタではなく、データのコピーをキューに入れることを検討してください。これにより、所有権の問題が単純化されます。
    *   大きなデータを渡す場合は、データをヒープに確保し、そのポインタをキューで渡します。その場合、受信側のタスクがデータを解放する責任を持ちます。
*   **グローバル変数の回避**: タスク間のデータ通信にグローバル変数を使用するのは避けてください。避けられない場合は、必ずミューテックスで保護してください。

## 4. 遅延とブロッキング

*   **ビジーウェイトの禁止**: `while(!flag) {}` のようなビジーウェイトはCPUを100%消費し、他のタスク（特に低優先度のタスク）を飢餓状態に陥らせます。**絶対に使用しないでください**。
*   **ブロッキングAPIの使用**: 常に`vTaskDelay`、`xQueueReceive`、`xSemaphoreTake`などのタイムアウト付きブロッキングAPIを使用してください。
*   **周期的タスク**: `vTaskDelay()`をループ内で使用すると、処理時間によって実行間隔がずれていきます。正確な周期的実行が必要な場合は、`vTaskDelayUntil()`を使用してください。

## 5. 割り込みサービスルーチン (ISR)

*   **短く高速に**: ISRは可能な限り短く、高速に保ってください。時間のかかる処理はISR内で行わないでください。
*   **FromISRバージョンの使用**: ISR内からFreeRTOSの関数を呼び出す場合は、必ず`...FromISR`という接尾辞を持つバージョン（例: `xSemaphoreGiveFromISR`, `xQueueSendToBackFromISR`）を使用してください。
*   **ブロッキングの禁止**: ISR内でブロッキングする可能性のある関数（`vTaskDelay`、`xSemaphoreTake`（タイムアウトあり）など）を呼び出さないでください。
*   **処理の委譲**: ISRは、バイナリセマフォを解放するか、キューにデータを送信して、より優先度の高いタスクを起動させるだけに留めるのが良い設計パターンです。実際の重い処理はそのタスクに任せます。

## 一般的なRTOSパターン

*   **ドライバパターン**: 特定のハードウェアペリフェラル（例: センサー）を管理するための専用タスクを作成します。このタスクは、デバイスからのデータ読み取りやコマンド送信の要求をキュー経由で受け取ります。
*   **イベントループパターン**: 中央のタスクがキューでイベントを待ち受け、受信したイベントの種類に応じて適切なハンドラ関数を呼び出します。ESP-IDFの`esp_event_loop`はこのパターンの良い例です。
*   **モニタータスク**: システムの健全性（各タスクのスタック使用量、空きヒープサイズなど）を定期的に監視し、ログに出力したり、異常時に警告を発したりするタスク。
