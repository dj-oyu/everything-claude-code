# メモリ管理ルール

このドキュメントは、ESP32/ESP32-P4プラットフォームにおけるメモリ管理の重要なルールとベストプラクティスを定義します。メモリは組み込みシステムで最も制約の厳しいリソースの一つであり、その使用には細心の注意が必要です。

## コア原則: メモリは希少なリソースである

*   **意図的に使用する**: メモリを確保する際は、そのサイズ、寿命、配置するメモリの種類（SRAM/PSRAM）を常に意識してください。
*   **倹約を心がける**: 不要なメモリ確保は避け、最小限のメモリで機能が実現できないか常に検討してください。
*   **計測と監視**: 静的解析（`idf.py size`）と動的解析（ヒープ/スタック監視関数）の両方を用いて、メモリ使用量を継続的に監視してください。

## 1. スタック vs. ヒープ

### スタックメモリ (`Stack`)

*   **用途**: 小さく、生存期間が短い変数（関数のローカル変数など）に使用します。
*   **注意点**:
    *   大きな配列や構造体をスタック上に宣言しないでください。スタックオーバーフローの原因となります。
    *   各タスクのスタックサイズは`menuconfig`や`xTaskCreate`で設定されますが、これは有限です。
*   **監視**: `uxTaskGetStackHighWaterMark()`を使用して、タスク実行中のスタックの「最高水位」を監視し、スタックサイズが適切か（大きすぎず、小さすぎず）を判断します。

### ヒープメモリ (`Heap`)

*   **用途**: 大きなデータ構造や、関数呼び出しを超えて生存期間が続くオブジェクトに使用します。ESP-IDFでは`heap_caps_malloc()`を使用します。
*   **ルール**:
    *   `heap_caps_malloc()`の戻り値は**必ず**`NULL`でないかチェックしてください。
    *   `heap_caps_malloc()`で確保したメモリは、不要になったら**必ず**`free()`で解放してください。
    *   確保 (`malloc`) と解放 (`free`) は、同じ責務を持つコードブロック（同じ関数やコンポーネント）内で行うのが理想です。

## 2. メモリリークの防止

*   **`malloc`と`free`のペア**: コードパス上のすべての`malloc`（または`calloc`など）に対応する`free`が存在することを確認してください。
*   **エラーパスの考慮**: 関数がエラーで早期リターンする場合、それまでに確保したメモリがすべて解放されていることを確認してください。`goto`ステートメントは、このようなクリーンアップ処理に有効な場合があります。
    ```c
    esp_err_t complex_function(void) {
        char *buffer1 = NULL;
        char *buffer2 = NULL;
        esp_err_t ret = ESP_OK;

        buffer1 = malloc(1024);
        if (!buffer1) { ret = ESP_ERR_NO_MEM; goto cleanup; }

        buffer2 = malloc(2048);
        if (!buffer2) { ret = ESP_ERR_NO_MEM; goto cleanup; }

        // ... 処理 ...

    cleanup:
        free(buffer1); // buffer2がNULLでも安全
        free(buffer2);
        return ret;
    }
    ```
*   **実行時監視**: 開発中、`heap_caps_get_free_size()`を定期的にログ出力し、システムの空きヒープサイズが一方的に減少し続けないか（メモリリークの兆候）を監視します。

## 3. メモリタイプの選択 (`heap_caps_malloc`のcapabilities引数)

### `MALLOC_CAP_INTERNAL` | `MALLOC_CAP_8BIT`
*   **説明**: ESP32の内部SRAM。最も高速にアクセスできます。
*   **用途**: パフォーマンスが重要なデータ、タスクのスタック、頻繁にアクセスされる変数。

### `MALLOC_CAP_SPIRAM` | `MALLOC_CAP_EXTRAM`
*   **説明**: 外部PSRAM。大容量ですが、内部SRAMよりもアクセスが遅いです。
*   **用途**: 大きなバッファ（例: カメラのフレームバッファ、LVGLの描画バッファ、ネットワークペイロード）、アセット、頻繁にはアクセスされないデータ構造。
*   **注意**: PSRAMの帯域幅は有限であり、複数のタスクやハードウェア（例: JPEGデコーダ、PPA）が同時にアクセスするとボトルネックになる可能性があります。

### `MALLOC_CAP_DMA`
*   **説明**: DMA（ダイレクトメモリアクセス）コントローラがアクセス可能なメモリ領域。
*   **用途**: SPI、I2S、LCDなどのペリフェラルがデータを送受信するために使用するバッファ。DMAを使用しないペリフェラル通信はCPU負荷が非常に高くなるため、これは必須です。

## 4. ヒープの断片化（フラグメンテーション）

*   **問題**: 小さなメモリの確保と解放を繰り返すと、空きメモリの合計は十分でも、連続した大きなブロックが確保できなくなることがあります。
*   **対策**:
    *   可能な限り、アプリケーションの起動時に大きなメモリチャンクを一度に確保し、終了時に解放するように設計します。
    *   同じサイズのオブジェクトを頻繁に生成・破棄する場合は、カスタムのメモリプール（オブジェクトプール）を検討します。
    *   `heap_caps_get_largest_free_block()`を監視し、断片化の進行度を把握します。

## 5. Flashメモリの活用 (`const`データ)

*   `const`修飾子を付けた初期値付きの変数は、RAM（`.data`セクション）ではなくFlashメモリ（`.rodata`セクション）に配置されます。
*   これにより、RAMを大幅に節約できます。ルックアップテーブル、設定文字列、UIアセットなどの大きな読み取り専用データには積極的に`const`を使用してください。
